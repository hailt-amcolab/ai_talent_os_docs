# FOF 非機能要件設計書

本書は FOF の非機能要件を、IPA「非機能要求グレード」の 6 大項目（可用性／性能・拡張性／運用・保守性／移行性／セキュリティ／システム環境・エコロジー）に沿って整理したものである。各項目について、(1) Foundation Design で決定済みの方針、(2) M1 納品時点の実装・設定、(3) 確定事項と後続マイルストーンでの確認事項 を分けて記載する。

目標値は、お客様のご回答（Q&A）を根拠として記載する。ご回答で数値目標を設けないとされた項目には、本書でも数値を設定しない。本番環境の構築時に決める事項は、時期（M4 など）を明記する。

## 1. 前提

- 利用者規模：同時アクセスは社内とクライアントを合わせて 20 名程度（当面）、通常操作の応答は 2 秒以内を目安とする（Q&A-phase0 No.85）。サービスオファーは 22 件。
- Phase 1 は 1 社（テナント）運用である（FD-ARCHITECTURE-001 §4）。
- 本番環境は未構築であり、本書の「実装」欄は主にアプリケーションと開発・ステージングの設定に基づく（[システム構成設計書](../architecture/README.md) §3）。

### 2.2 実装状況

| 項目 | 実装・設定 |
|---|---|
| サーバ構成 | ステージングは Web・ジョブ・Redis 互換ストア・DB を 1 台に配置。本番のサーバ台数・冗長化は本番環境の構築時（M4）に定める（AV-04） |
| ヘルスチェック | `GET /up`（プロセスの生存のみ判定） |
| DB バックアップ | バックアップ・PITR は本番リリース時に設定する（FD-DEPLOYMENT-003 の適用範囲）。ステージング DB は Docker ボリュームのみ |
| Redis 永続化 | データディレクトリをホストにマウント。永続化方式（RDB/AOF）は明示せず、イメージの既定値 |
| ファイル保持 | ステージングのアップロードファイル・請求書 PDF は Docker ボリュームで保持し、デプロイで消えない |
| ジョブ再試行（共通） | ジョブ共通の再試行設定はない。未捕捉の例外は Sidekiq の既定リトライに従う。メール送信と freee 連携はアプリ側で制御する（3.3） |
| freee 連携の障害時 | 取引登録は 1 回だけ試行し、失敗した場合は送信状態を「失敗」として記録する。自動再試行は行わず、原因を解消した後に運用担当が再送する。freee へ送った取引を FOF から編集・削除することはなく、取消は逆仕訳の追加で表す |
| freee 接続の維持 | トークンの有効期限 5 分前に利用時更新し、加えて毎時の定期ジョブで期限 90 分以内なら更新する。リフレッシュトークンは 1 回限りのため、更新は行ロックで直列化する |
| 監査ログのパーティション | `audit_events`・`state_transitions` は月次パーティション。マイグレーションで 2028-01 までを作成済みで、日次の定期ジョブ（02:30）が常に 3 か月先までのパーティションを作成する（行レベルセキュリティ・追記専用トリガー・権限を同時に設定）。作成できなかった場合はエラーログを出力する |

### 3.3 外部連携の流量・再試行制御

| 対象 | 制御 |
|---|---|
| freee API | 専用キューを並列度 1 で処理（レート制限への対応）。取引登録は 1 回の実行で 1 試行、自動再試行なし（接続確立のタイムアウトのみ 2 回まで再接続）。状態取得は HTTP 429 を受けた時点でその会社の実行を打ち切り、残りは次回の実行で取得する |
| freee トークン | 毎時の定期更新に加え、利用時に期限 5 分前なら更新。更新が拒否された場合は再接続が必要となり、再接続までの送信・状態取得は「認証不可」として失敗を記録する |
| メール送信 | 最大 5 回（初回含む）、再試行間隔 1・2・5・10 分＋最大 20% のゆらぎ。請求書メールは 1 回のみ（FD-MAIL-003 §1.2） |
| Web フォーム受付 | IP 単位で 1 分 5 件・1 時間 30 件。冪等キー保持 24 時間、同一内容判定 10 分 |

## 5. 移行性

### 5.1 決定済みの方針

| 項目 | 内容 | 根拠 |
|---|---|---|
| スキーマ移行 | マイグレーションは障害復旧後のデータベースでも先頭から再実行できること。本番データを手作業で修正した状態に依存しない | FD-DEPLOYMENT-003 §2 |
| 稼働後のインデックス追加 | データのあるテーブルには `CREATE INDEX CONCURRENTLY` を用い、他のマイグレーションと分離 | FD-DATA-003 |
| 物理削除の禁止 | 業務データは物理削除せず業務状態またはアーカイブで表現。アプリ用 DB ロールには DELETE 権限を付与しない（例外は `staged_uploads`・`freee_connections` の 2 テーブル） | FD-DATA-002 |

### 5.2 実装状況

| 項目 | 実装・設定 |
|---|---|

## 6. セキュリティ

### 6.1 決定済みの方針

| 項目 | 内容 | 根拠 |
|---|---|---|
| 社内利用者認証 | Google Workspace による SSO（OIDC）。FOF に登録済みのメンバーだけがログインできる。招待リンクによる登録は行わない（2026-10-29 決定） | FD-AUTH-001 |
| セッション | サーバ側セッション、HttpOnly Cookie、CSRF 対策（Origin/Referer 許可リスト＋ダブルサブミットトークン）、承認待ち利用者向けの制限付きセッション。絶対有効期限 480 分・無操作タイムアウト 30 分を初期値とし、管理者が設定変更可能 | FD-AUTH-003 |
| ポータル利用者セッション | 別系統のセッション管理 | FD-AUTH-002 |
| 認可 | ロール × オブジェクト × 操作 × 範囲の権限マトリクス | FD-AUTHZ-001 |
| テナント分離 | RLS による会社単位の分離。アプリ用 DB ロールは RLS を回避できず、テーブル所有者と分離 | FD-DATA-003、FD-DEPLOYMENT-007 |
| シークレット管理 | 環境ごとに分離、リポジトリに値を置かない、アクセス制御付きストア、本番の参照記録 | FD-DEPLOYMENT-006 |
| ファイル | 共通のファイル管理、マルウェアスキャン（スキャン完了まで隔離、スキャン失敗は不合格扱い）、権限付きダウンロード | FD-FILE-001 |
| 外部入力の表示 | 外部から受信した内容の表示時のタグ除去、外部リソースの自動読込禁止 | FD-SECURITY-005 |
| 外部送信データ | 外部システムへ送るデータの最小化（既定拒否） | FD-INTEGRATION-004 |

### 6.2 実装値

| 項目 | 値 |
|---|---|
| セッション絶対有効期限 | 480 分（既定値。設定で変更可） |
| 無操作タイムアウト | 30 分（既定値。絶対有効期限以下であること） |

| freee OAuth の CSRF 対策 | リダイレクト方式では、署名付き Cookie に保持した state と freee からの戻り値の一致を確認する |
| freee への高額取引の送信 | 50 万円以上の消込仕訳は、承認（Domain Lead → Control Lead → Executive Owner）を経てから送信する |
| コンテナ | 非 root ユーザ（UID 1000）で実行 |
| 静的検査 | Brakeman、bundler-audit（CI は手動実行） |
